## 1. 何を作るか

兵庫県の元織物工場の中で、コーヒーの幼木を育てている。毎日、温度・湿度・土の水分を見て、
「加湿器をいつ何分動かすか」「水をやるか待つか」を人が決めている。

この「毎日見て決める」仕事を、**一度に全部ではなく、人の操作から経験を貯めながら、だんだん任せていく**。
決める頭は**役割の違う 3 体のエージェント**。エージェントが出すのは**計画だけ**。計画を入／切に変えるのは、決まった規則で書いた**守りの層（コード）**。
守りの層を通った指示だけが、本物の加湿器（スマートプラグ経由）か、模擬の栽培室に届く。

### 4 つの段（任せる度合いが上がる順・v0.7 で 3 → 4）

```
手動 ─────→ 定時 ─────────→ 定時・長さは AI ──→ オート
人が入切    時刻も長さも人   時刻は人・分は AI    時刻も分も AI
            （コード・AI なし）（開始の 10 分前に計画）（毎 3 時間の定時の起動）
```

| モード | 誰が決めるか | 中身 | 守りの層 |
|---|---|---|---|
| **手動** | 人 | 画面のトグルで入・切（`set_humidifier`） | 通す |
| **定時** | コードのタイマー（**AI なし**） | 例：毎日 12:00 に入れて 60 分で切る（`set_timer`＝入切・開始の時刻・分） | 通す |
| **定時・長さは AI** | 時刻＝人・分＝制御役 | 定時の切り替え「長さを AI に任せる」（`set_timer` の `ai_minutes`）。開始の 10 分前に計画のセッションを起こし、「開始は 12:00 に決まっている・分だけ決める」と渡す。答えは `submit_plan`（開始の時刻が違えば断る）。**答えが来ない・断った時は人の既定の分**で動かす＝定時は必ず定時に動く。どちらで動いたか・理由（どの経験を使ったか）を操作の記録と画面に残す。1 日 1 回・約 6¢ | 通す |
| **オート** | エージェント | 狙いの VPD に向けて、開始の時刻と運転の分を計画で出す（`submit_plan`）。オートの入切＝定時の起動（deployments）の `pause`／`unpause`（`set_auto`） | 通す |

- どれも同時に入っていてよい。どれが出した運転も、守りの層の同じ帳簿（連続・1 日の合計・間）に数える。手動の「切」と「止める」はタイマーやオートの運転より強い。
- どのモードの操作も**操作の記録**に「誰が」を付けて残す＝オートのエージェントが振り返る材料になる（§4）。人がトグルで入れた回も、タイマーが入れた回も、「入れたら何分で VPD がいくつ動いたか」の経験になる。

### 設計の芯
- **センサーの層を、動かす機械から独立させる**。AI は機械を直接触らない。
- **どんな計画が来ても、守りの層の上限は越えない**（テストで機械的に確かめる）。
- **経験は真似でなく効き目**：過去の操作をお手本にせず、「この操作でこう動いた」の事実だけを貯めて次の計画に使う。
- 理由には必ず**数値と時刻**を引く。人が読む文と、機械が読む JSON の両方を残す。
- 「最適」とは言わない。季節や状態に合った運転を、データから出す（季節のモードは作り込まない）。

- **公式の API ではない**（気象庁の画面の裏の JSON）＝形が変わる・取れない時は **「天気は無し」で今までどおり動く**（止めない・画面に「天気：取れていない」）。

**★この期間の性質**：記録の期間は、結果として**根の生長が芳しくなく、水のやりすぎを疑っている**期間。
実際にやった運転は**お手本ではない**。評価では「やったこと」ではなく「後から見て正しかったこと」を正解に置く（§7）。
原因は断定しない（疑いのまま扱う）。

## 3. 全体の絵

```
  温湿度計（クラウド 30 秒ごと）／再生の記録（CSV）
        │
        ▼
  受け手（手元に常駐・launchd）
   ├─ 正本の記録：run/meter_*.jsonl（温湿度・VPD）・run/control_*.jsonl（操作の記録）
   ├─ センサーの自己点検・穴（記録なし）の見分け
   ├─ 定時のタイマー（コード・AI なし／長さだけ AI に聞く）
   ├─ 外の天気（気象庁のアメダス 10 分ごと・予報は発表の後）→ 要約（コード）
   ├─ 自前の MCP サーバー ◀── Mac の Claude アプリの Artifact
   │    （チャート・トグル・定時の入切・オートの入切・止める）
   └─ 写し ──────────────┐ 温湿度：1 時間 1 ファイルの CSV を 5 分ごと
                          │ 操作：1 件ずつ
                          │ 天気：要約（/weather/…）
                          ▼
  ┌──────── Managed Agents（定時の起動で起きる＝オート）────────┐
  │ 記憶の置き場：温湿度の記録・操作の記録・経験（版つき）＋知識 │
  │ ① 振り返り：記録の分析役が前回からの操作の効き目を計算     │
  │     → 経験を更新（前の版を読んでから書く）                 │
  │ ② 計画：制御役が経験を読んで submit_plan（custom tool）    │
  │   （栽培の専門家は知識を読むだけ）                         │
  └──────────────────────┬────────────────────────┘
                         │ 計画（受け手が見に行って受け取る）
                         ▼
       守りの層（決まった規則・「止める」が最優先）◀── 手動のトグル・定時のタイマーも同じ
             │ 入／切
          ┌──┴──────────────────┐
          ▼                      ▼
   模擬の栽培室            スマートプラグ → 加湿器
   （評価・再生）           （本物・人が付いている時）
```

- 手動のトグル（MCP）も、定時のタイマー（コード）も、オートの計画（custom tool）も、**同じ守りの層**を通る。
- エージェントは**常駐しない**。起きるのは定時の起動（オートが入っている時）だけで、起きるたびに「振り返り→経験→計画」を 1 回通して眠る。毎分の見張りは受け手（コード）の仕事。

## 4. 3 体のエージェント

| 役 | モデル・effort | 持つ道具 | 記憶 | 返す物 |
|---|---|---|---|---|
| **制御役**（取りまとめ・決める） | Opus 5.5・medium | 「運転の計画を出す」（custom tool）・読み取り | 経験＝読む・温湿度と操作の記録＝読む | その時間・その日の運転の計画（開始の時刻・分）・理由（数値と時刻・どの経験を使ったか）・状態（大丈夫／注意）・水やりの提案（人へ） |
| **記録の分析役** | Sonnet 5.5・medium（計算は作業場の Python） | 作業場の Python（pandas）・読み取り | 温湿度と操作の記録＝読む・**経験＝書く** | 前回からの操作の効き目（入れた→何分で VPD がいくつ動いた・狙いに届いたか・断られたか）・直近の傾向・疑わしいセンサー |
| **栽培の専門家** | Haiku 5.5・medium（知識を読むだけ） | 読み取り | 栽培の知識＝読むだけ | 今の時期・今の状態で木が要る物・避けること・その出どころ |

### 起動のたびの流れ（振り返り→経験→計画）
1. 受け手が、セッションを始める前に今の時間の温湿度の CSV を 1 回写す（最新まで置き場に載せる）。
2. **振り返り**：分析役が、経験の今の版を読み、前回の起動からの操作の記録と温湿度の記録を Python（pandas）で読んで、操作ごとに前後の VPD の差を自分で計算する。数える物＝誰が（手動／定時／オート）・入れた時刻と分・入れる前の VPD・入れて 15／30／60 分の VPD・狙いの帯に届いたか・守りの層に断られたか（理由）。**穴（記録なし）にかかる操作は効き目を数えない**。
3. **経験の更新**：分析役が経験を書き直す（前の版を読んでから・版の数と「誰が書いたか」は置き場が残す）。
4. **計画**：制御役が経験と今の値を読み、狙いの VPD に向けて `submit_plan`（開始の時刻・分）を出す。理由にはどの経験の行を使ったかを引く。受け手が見に行って受け取り、守りの層を通して結果を返す。断られたら直して出し直してよい。

### 外の天気を読む（v0.7・農家の読み）
- nori の考え：「今日だけを見ると加湿器を入れた方がよいが、明日は雨が降るから、ここはあえて止めておこう」。先の天気を読んで**控える／長くする**判断を、制御役（計画）と分析役（振り返り）に足す。
- **計画**：依頼文に、今の外（近くのアメダスの気温・湿度・直近の降水）と今日・明日の予報（天気の文・降水確率・気温）を**数行の字**で入れる（生の JSON は入れない）。「今日だけを見ると入れたいが、先の天気で控える／長くする」を許す。**「今日は入れない」も正しい計画**＝`runs` を空にして理由を書く（`submit_plan` は空の runs を「この出し手は入れない」として受ける）。根拠の evidence に気象も入れてよい（device＝「アメダス」「予報 兵庫県」）。天気が取れていなければ依頼文に「天気は無し」と書く。
- **見た予報を残す**：計画を受けた時、操作の記録（`what=計画`）に `weather`（その時に渡した要約）を付ける＝置き場の操作の記録にも写る。
- **振り返り**：農家が年々覚える物を経験に貯める。「雨の予報で控えた → 部屋の湿度は本当に上がったか」「外の湿度が上がってから部屋が何時間遅れで上がるか」「予報は当たったか（翌日のアメダスの降水と比べる）」。**この部屋で外の天気が本当に効くかは決めつけず、記録で確かめる**（工場は閉じていない＝夏の 72〜97% は外の影響が大きい見込み）。
- 置き場：新しく作らず、**温湿度の置き場（`saibai-meter`）の中の別のファイル**に写す＝`/weather/YYYY-MM-DD.csv`（アメダスの 1 時間値・列＝時刻・気温・湿度・降水・日照）と `/weather/forecast.md`（最新の予報の要約・発表の時刻つき）。理由：定時の起動と計画のセッションは今の置き場をすでに読んでいる＝定時の起動を作り直さずに済む（1 セッション 8 つの上限にも余裕を残す）。
- **守りの層は替えない**（天気は計画を変えるだけ・線は越えない）。
- 費用：依頼文が数百字増えるだけ（1 起動 10¢ はほぼ変わらない）。

### 定時・長さは AI（v0.7）
- 開始の時刻は人（画面の [12:00]）、分は制御役。受け手が**開始の 10 分前**に計画のセッション（制御役＋専門家・全部読むだけ）を起こし、「開始は 12:00 に決まっている・分だけ決める・既定は 60 分」と、今の値・天気の要約を渡す。
- 答えは `submit_plan`。開始の時刻が人の時刻と違えば断る（直して出し直してよい）。分は守りの層の 1 回の上限まで。0 分（空の runs）＝「今日は入れない」も受ける。
- **開始の時刻までに答えが来ない・断られたままなら、人の既定の分で動かす**＝定時は必ず定時に動く。どちらで動いたか（「AI の分」／「既定の分・理由」）と、AI の理由を操作の記録と画面に残す。
- 費用：1 日 1 回の計画のセッション（約 6¢）。

### 経験の貯め方（真似でなく効き目）
- 貯めるのは「**この操作で、こう動いた**」の事実だけ（例：「11/5 12:00・オート・30 分入れた・VPD 0.71→0.48（30 分で −0.23）・狙いに 22 分で届いた」）。そこから引いた傾向（例：「15℃台の夜は 15 分で約 −0.1 kPa」）は、もとにした回の数と一緒に書く。
- **最初の経験**に夏と秋の作業の記録（`data/actions_*.csv`）を使ってよい。ただしその期間は水のやりすぎを疑っている（§2）＝**操作をお手本にしない**。「いつ入れたか」は真似せず、「入れたらどう動いたか」だけを取る。
- **予測は過去の記録だけで**：評価の再生（§7）では、その時点より先の値を経験にも作業場にも渡さない。

### 記憶の置き場（3 つ＋知識）
資料の性質：セッションの外から API で書ける・書くたびに版と「誰が書いたか」が残る・1 件 100KB まで・1 つの置き場に 10,000 件まで・1 セッションに 8 つまで・版は 30 日で消えうる・**鍵は入れない**。
**正本は手元の記録**（`run/*.jsonl`）。置き場はエージェントが読むための写しで、消えても手元から作り直せる。

| 置き場 | 書く人 | 中身・形 |
|---|---|---|
| 温湿度の記録 | 受け手（API） | **1 時間 1 ファイルの CSV**（`/meter/YYYY-MM-DD/HH.csv`・30 秒ごと 120 行・約 5KB・列＝読んだ時刻・温度・湿度・VPD）。5 分ごとに今の時間のファイルを書き足す（前の版の sha を `precondition` にして上書き）・時間が変わったら閉じる。1 日 1 ファイルは約 115KB で 1 件の上限を越えるので取らない |
| 操作の記録 | 受け手（API） | 1 件ずつ（1 日 1 ファイル `/actions/YYYY-MM-DD.jsonl` に追記）。中身は §5 の「操作の記録の 1 件」 |
| 経験 | 分析役（セッションの中） | 振り返りの結果（`/experience.md`）。版の一覧（誰が・いつ）が「経験が育つ」の元 |
| 栽培の知識 | 人（最初に 1 回） | `knowledge_seed.md`・読むだけ |

- 書けなかった分は手元に残し、次の回に送り直す。
- **役ごとの読み書き＝1 回の起動を 2 段のセッションにする（段 B で決めた）**。資料（claude-api の手引きの multiagent と memory の節）では、名簿の中のエージェントは**1 つの作業場とファイルを共にし**、置き場の `access` は**セッションにつなぐ時に 1 つだけ**決まる＝同じセッションの中で役ごとには分けられない。(a) 指示で「経験に書くのは分析役だけ」とする案は、守らせる物が文だけになり、版の「誰が書いたか」もセッションまでしか分からない。そこで (b) を取った：
  1. **振り返りのセッション**（分析役が主）：経験＝書ける・温湿度と操作の記録＝読むだけ。
  2. **計画のセッション**（制御役＋専門家）：経験・記録・知識＝**すべて読むだけ**＝制御役は経験を書き換えられない（ファイルの層で断られる）。
  - 良い所：経験の版の `created_by` のセッション ID が、そのまま「振り返りが書いた」の印になる。振り返りの分の費用がセッションごとに別に出る（段 C の「振り返りでどれだけ増えるか」）。
  - 定時の起動（オート）が起こすのは振り返りのセッション。受け手はそれが止まるのを見に行き、計画のセッションを続けて起こす（同じ 1 回の起動として記録する）。
  - 定時の起動は毎 3 時間（`0 */3 * * *`・東京）＝守りの層の「計画が 3 時間来なければ切」と合う。費用の上限は定時の起動（振り返り）$0.50・計画のセッション $1。1 回 10〜17¢（11/4 に 2 回叩いた・うち振り返り 4〜6¢）。経験の最初の版は夏と秋の記録からコードで計算した物（api_actor）、後の版は振り返りのセッションが書く（session_actor）。
- **11/4 に叩いて確かめた**：読むだけでつないだ置き場に書くと、`bash` の追記は `Read-only file system`、`edit` は `OSError: [Errno 30]` で断られ、版は増えなかった。分析役は置き場の 1 時間 CSV を pandas で読み、秋の 10/4 01:40 の入（手動・280 分）の前後の VPD を 0.862→15 分 0.617（−0.245）・30 分 0.562（−0.300）・60 分 0.447（−0.415）と出した＝手元で同じ行を引いて全部一致。

- **モデルと effort は役ごとに明示する**（nori・11/4＝指定しないと高くつく。既定は Opus 5.5＝medium・Sonnet 5.5＝high）。エージェントの `model` を `{"id": ..., "effort": ...}` で書く（`src/saibai/agents.py` の `MODELS`・`uv run saibai-agents models` でそろえる）。
  - 落とし穴 ①：セッションごとに `model` を差し替える時は、差し替えの中にも `effort` を書く（差し替えは `model` を丸ごと置き換える＝書かないとそのモデルの既定の effort で走る）。今は差し替えを使っていない。
  - 落とし穴 ②（11/4 に叩いて分かった）：エージェントを更新しても、**定時の起動と名簿は保存した時の版に留まる**（定時の起動は分析役の版 1・制御役の名簿は専門家の版 1 のままで、更新の後の 1 回目の起動は Sonnet の high で走った）。更新したら版を留め直す（`saibai-agents models` が続けてやる）。
- 仕事を渡せるのは 1 段まで（制御役 → 2 体）。2 体は制御役の会話を見ない＝渡す仕事に「読む場所・聞きたいこと・返す形」を必ず書く。
- 比べる相手として、**制御役 1 体が全部を自分でやる設定**も同じ指示文の骨で持つ（§7）。
- 水やりは機械で動かさない（人の作業）＝頭脳は「灌水を控える／待つ／やる」を**人への提案**として出す。
- **人への一言（v0.8）**：`submit_plan` に任意の欄 `to_person`（数行・機械に触らない事＝水やりなど）。**守りの層はこの欄を読まない**＝この欄で機械は動かない（テストで確かめる）。操作の記録の「計画」の 1 件に残し、画面に 1 行で出す。実機には土の計器が無い＝実機では土の数値は渡さない（空のまま）。再生では `soil_a` を温湿度の記録の列として渡す。「何以上なら水を控える」の線は渡さない（正解を見た後に引いた線になる）。

### Managed Agents の機能と、現場で要る理由（1 対 1）

| 機能 | 現場で要る理由 | 使い方 |
|---|---|---|
| 役割の違う複数のエージェント | 記録の計算・作物の知識・運転の判断は、見る物も道具も違う | 制御役＋分析役＋専門家 |
| 手元で実行する道具（custom tool） | 機械を動かす口を AI の外に置く＝守りの層を必ず通す | 「運転の計画を出す」を制御役だけに |
| 記憶の置き場（読むだけ／書ける・版が残る・外から API で書ける） | 栽培の知識は変えさせない／操作の効き目を積み、いつ何を学んだかを後から見せる／記録は受け手が外から写す | 温湿度の記録・操作の記録（受け手が写す）・経験（分析役が書く・版）・知識（読むだけ） |
| 作業場の中の Python | 記録を AI の頭に全部入れない＝計算はコードで | 分析役が置き場の CSV を pandas で読み、操作の前後の VPD の差を計算する |
| 定時の起動（cron・東京時間） | 人がいなくても決める＝オートの入切そのもの | 起動のたびに振り返り→経験→計画。オートの入切＝`pause`／`unpause` |
| 1 回ごとの費用の上限 | 無人で回しても請求が暴れない | セッションに上限 |
| 出来の採点（outcome） | 計画が「理由に数値と時刻を引いているか」などを別の文脈で採点し、通るまで直させる | 毎朝の計画だけ（費用） |

使わない物：その場で役を作る機能（名簿の 3 体に固定）・大量の並列の仕組み（1 日分の記録では要らない）。

## 5. 守りの層（AI では書かない・決まった規則のコード）

| 線 | 値（再生・評価） | 値（本物の実機・人が付く日） | 値（実機デモ・v0.7） |
|---|---|---|---|
| 入れない湿度（入れる前） | `node_a` の RH が 75% 以上なら入れない | 同じ | **無し** |
| 止める湿度（運転中） | 85% に届いたら計画の残りに関わらず切る | 同じ | **無し** |
| 連続運転の上限 | 180 分 | **60 分** | 60 分 |
| 1 日の合計 | 360 分 | **120 分** | 120 分 |
| 入と入の間 | 切ってから 1 分あける（連打で入切がばたつかないための下限・v0.6 で 30 分から短くした＝デモと試しの間は 30 分は過剰） | 同じ |
| 古い値で動かさない | 最新の湿度が 5 分より古ければ入れない・運転中なら切る | 同じ（§8 の読み方で鮮度を測る） |
| 疑わしいセンサー | 温度と RH が**そろって 90 分**変わらない・1 分で 10 pt 以上跳ぶ時、その値を根拠にした計画を断る・今すぐの入は断る | 同じ |
| 効かない運転 | 入れて 15 分たっても RH が入れた時より 1 pt も上がらなければ切り、その回の残りを捨てる | 同じ（§8 の止まりの見分け ②） |
| 計画が来ない時 | 3 時間来なければ切 | 同じ |
| 手で止める | **すべてに優先**（Artifact の「止める」・受け手の起動時は必ず切から始める） | 同じ |
| 計画に無い「入」 | — | 受け手が**毎分プラグの状態を読み**、計画に無い「入」なら切る（プラグは停電から戻ると前の状態に戻るため） |
| 人が居ない時 | — | **加湿器をプラグにつながない**（受け手と工場が両方止まると毎分の点検が効かない・加湿器は通電で運転し水切れの検知も無い）。定時の起動は、空のプラグか電気スタンドで回してよい |

- **実機デモの組**（v0.7・nori 11/4）：デモは実機で人が付いて動かす。工場の湿度では 75%／85% の 2 本がすぐ効いて加湿器が動く所を見せられない＝`[guard.demo]` で 2 本を「無し」にする。**ほかの線（連続 60 分・1 日 120 分・古い値・止まり 90 分・15 分で上がらなければ切る・止めるが最優先・起動は切・計画に無い入を切る）は残す**。組は受け手の起動の時に選ぶ（`SAIBAI_GUARD=demo`・既定は `real`）。どの組で動いているかを起動のログ・`get_status` の `guard.set`・画面（「デモ：湿度の線は止めている」）に出す。**再生・評価の数字はデモの組で取らない**。計画の依頼文の線も今の組から作る（止めた線は書かない＝制御役が字を読んで入れない計画を出さないように）。
- **線の値は設定ファイル 1 つ**（`config/saibai.toml`）にまとめる。本番に戻す時（例：入と入の間を 30 分に）はそこだけ書き換える。コードに数を散らさない。
- **3 つのモードとも同じ守りの層・同じ帳簿**。手動のトグル＝「今から n 分」の計画・定時のタイマー＝決まった時刻に「n 分」の計画・オート＝エージェントの計画。どれも同じ線で断られる。
- **帳簿は起こし直しても数え直さない**：受け手は起動の時に `run/control_*.jsonl` から今日動いた分と最後に切った時刻を読み戻す（起こし直すたびに 1 日の上限が 0 に戻らない）。
- **操作の記録の 1 件**（`run/control_*.jsonl` が正本・置き場へ写す）＝時刻・誰が（手動／定時／オート／守りの層／外から）・何を（入・切・予定の分）・受け付けた／断った（理由）・3 秒後に読み直したプラグの状態・その時の温度・湿度・VPD。「外から」＝毎分の点検で、記録に無いプラグの変化を見つけた時。
- **穴を穴として残す**：最後の読みからの空きが 2 分を越えたら「何時から何時まで記録なし（受け手が止まっていた）」を 1 件残す。戻った時にプラグの状態が変わっていれば「外から・時刻は空きの間のどこか」。振り返りでは穴にかかる操作の効き目を数えず、チャートでは穴を線でつながない。Mac が眠る・閉じる間は記録が抜ける（SwitchBot のクラウドに過去の値を取る口は無い＝取り戻せない）＝受け手は `caffeinate -s` で包む（電源につないでいる間は眠らない）。蓋を閉じても止めない設定（`pmset`）は人の手。
- 断った時は、**断った理由を道具の結果として制御役に返す**＝制御役は直した計画を出し直せる。画面にも出す。
- 「実運転」の再生（§7）だけは、記録をそのまま流す＝守りの層に掛けない（掛けると全部断られる）。
- **テスト**：どんな計画（ランダムに大量）を渡しても上限を越えない、を機械で確かめる。

## 6. 模擬の栽培室（v0.8 で書き直し）

- 動かすのは加湿器だけ＝**湿り気（絶対湿度 AH・g/m³）の動きだけ**を合わせる。温度は記録をそのまま流し、RH と VPD は AH と記録の温度から出す（AH＝2167·e／(T＋273.15)・e＝RH／100·e°(T)・e°は VPD と同じ式）。機器は `node_a`（室の空気の基準）。

### 合わせる式（誤差の表と k・g・c を決めるため）
```
dAH/dt = −k·(AH − AH_外(t)) + s + g·加湿器(t) + c·冷房装置(t)
```
- AH_外＝段 1 の近くのアメダスの毎正時の気温と湿度から出した AH を、時刻で直線に内挿。
- s＝部屋の湿り気の素（鉢と床からの蒸発・木の蒸散・人）。抜けが外へ向かうだけだと、室が外より湿っている分を説明できない＝定数を 1 つ置く。
- 加湿器・冷房装置＝入っている間 1。**冷房装置（`cool_a`・水をかけて冷やす型）は頭脳が動かさない**＝外の天気と同じ「4 通りに共通の入力」。記録は止めた時だけ＝ふだんは動いていた見込み（夏の窓の中に 9/4 03:30〜16:00・9/4 19:30〜9/5 11:00・9/8 00:20〜08:30・9/8 15:00〜（再開の記録なし＝窓の終わりまで止めたと置く））。秋は 0 と置く（秋の記録に冷房装置の行は無い）。
- 合わせ方：k を格子で振り、k ごとに s・g・c は線形の最小二乗（記録の AH から 6 時間ごとに出直した軌跡と記録の差）。
- **合わせる日と評価の窓を分ける**：夏＝8/22〜9/2（200 L の給水タンクをつないだ後＝水切れで止まりにくい・入切が記録どおり）・秋＝10/3〜10/19。どちらも窓の外。**ただし c だけは分けられない**＝冷房装置を止めた記録が夏の窓の中（9/4・9/8）にしか無い。合わせる日は冷房装置がずっと動いていた＝c は s に混ざる。そこで c は k・g・s を決めた後、窓の中の止めた区間だけで決める（c は誤差の表にだけ効き、再生の採点には効かない＝下の「再生の形」）。そう README にも書く。
- **天窓（9/8 00:05〜03:10）と天井の送風機（9/5 16:00〜）は項を足さない**＝その時間を「模擬が合わない区間」として印を付け、採点からは外さずに誤差の表に出す。水やりの後の蒸発も項を足さない（誤差に出たら README に書く）。秋の窓（10/20〜10/26）にはこの類の記録が無い（10/20 05:24 のブレーカーの 2 分だけ＝記録の穴）。
- **誤差**（季節ごと・合わせる日と窓の両方）：AH の差の中央と 90%（全体と、印の区間）・入れた 30 分の上がり幅（記録と模擬）・切った後の戻り方（切って 30・60 分の AH の下がり幅）。合わない所もそのまま README へ。
- **k が季節で違えば、それ自体が「夏と秋で運転が変わる」理由**になる（抜けが速い季節は、同じ分の加湿でも早く元に戻る）。

### 再生の形（記録＋加湿器の差だけを式で足す）
```
AH_模擬(t) = AH_記録(t) + Δ(t)
dΔ/dt = −k·Δ + g·(加湿器_模擬(t) − 加湿器_記録(t))
```
- 理由：外の値は十数 km 先の 1 時間値で、式だけで部屋の AH を流すと、その誤差（4 通りに共通）が運転の差より大きくなりうる。記録を土台にすると、**冷房装置・天窓・送風機・水やり・外の天気は記録の中にそのまま入り、4 通りに共通**になる。式で作るのは「記録と違う入切をした分」だけ（k・g は上の合わせる日から）。
- 実運転＝記録の入切そのまま＝Δ＝0＝模擬は記録と同じ。
- RH が 100% を越える所は 100% で止める（霧になって落ちる）。
- テスト：入れると上がる・切ると記録へ戻る（外へ向かう）・同じ入力なら同じ結果・合わせる式で作った作り物の記録から k・g を取り戻せる。

### 外の天気（再生）
- 過去の 1 時間値＝`data/weather_hourly_<区間>.csv`（段 1）。**過去の予報は手に入らない**＝再生では「その先の実際の値から作った要約」を予報として渡す（例「明日 9/5：雨（降水 12 mm・日照 0.5 時間）・最低 23℃・最高 29℃」）。字の形は受け手の要約（v0.7）にそろえる＝依頼文の読み方は変えない。**予報がいつも当たる＝本物より有利な条件**＝README にそう書く。天気の文の決め方（コード）：1 日の降水 1 mm 以上＝雨・日照 6 時間以上＝晴れ・ほか＝くもり。

### 先読みの禁止（コードとテストで守る）

- テスト＝窓の中のどの時刻でも、渡した記録・経験・天気の最後の時刻が再生の時計より前（予報の要約だけは「先の値から作った」と字で分かる形＝本物の予報に当たる物）。

### 水のやりすぎの疑い（人への一言）
- 制御役は `to_person` に、機械に触らない事（水やり）を書ける（§4）。再生では `soil_a` を記録として渡す。線（何以上なら控える）は渡さない。

## 8. 本物の口（実機）

| 物 | 役 | 読み方・動かし方 |
|---|---|---|
| スマートプラグ（SwitchBot プラグミニ） | 加湿器の電源の入／切 | SwitchBot のクラウド API（v1.1）で `turnOn`／`turnOff`・状態（電流）で本当に入ったかを確かめる |
| 温湿度計（SwitchBot 温湿度計プラス） | 木のそばの温度・湿度 | **受け手がクラウドを 30 秒ごとに読む**（読んだ時刻を手元で付ける）。Bluetooth の発信を直接読む道は、そばに機械を置ける時の見比べ・予備 |
| ハブミニ | 温湿度計とクラウドの橋 | 温湿度計と一緒に工場に置く |

- 鍵（トークンとシークレット）は手元の機械だけ（`.env`）。リポジトリにもエージェントにも渡さない。
- **プラグは停電から戻ると前の状態に戻る**（11/3 に現物で確認：入→入・切→切）＝§5 の 2 行で受ける。
- **Bluetooth の読み取りはターミナル（か自動起動）から動かす**：macOS は Bluetooth の許可をアプリごとに分ける。Claude のアプリの中からは断られた（11/3）。受け手もアプリの外で常駐させる＝会話を閉じても守りが止まらない。
- 1 日 1 万回の呼び出しの上限＝温湿度 30 秒ごと（2,880 回）＋プラグの状態 毎分（1,440 回）＋命令＝約 4,500 回＝足りる。10 秒ごとにすると温湿度だけで 8,640 回＝上限に当たる。
- **宿題：止まりの見分け**＝クラウドの温湿度には測った時刻が付かず、ハブや温湿度計が止まっても最後の値が返り続ける恐れがある＝§5 の「古い値で動かさない」がこのままでは測れない。次の順で確かめて決める：①ハブの電源を抜いた時にクラウドが何を返すか（オフラインの印や誤りが返るなら、それで止まりとする）②返らなければ、「加湿器が入っているのに湿度が上がらない」で切る（§5 の上限と合わせて切る側に倒れる）。
  - **11/4 夜に線を直した**：クラウドの湿度は整数で、工場の夜は 85 分のあいだ 67% のまま・温度も 45 分 15.3℃ のままだった＝「RH が 15 分変わらない」では、ふつうの夜をいつも「止まり」とみなし、画面のスイッチでも入らなかった。止まりの見分けは「温度と RH がそろって 90 分変わらない」（今夜の最長 45 分の倍）に緩め、代わりに ② の「入れて 15 分で 1 pt も上がらなければ切る」を先に入れた（加湿器は 30 分で +12〜16 pt＝15 分なら +6 pt 前後のはず）。プラグの先が空の試しでは、毎回 15 分で切れる。
  - **線の名前の取り違えに注意**：再生の記録（ラズパイ・小数 2 桁）でも同じ線を使う。小数 2 桁の値が 90 分そろって同じなのは、まず起きない。
- **11/3 夜の試しで分かったこと**（`docs/dev_log.md`）：
  - クラウドは**大きな変化ならすぐ上がる**＝息で 60→70% にした時、BLE の 6 秒後の読みにはもう出ていた。小さな変化（0.1℃）は 8 分上がらないことがある（11/3 昼）。
  - **Webhook は使わない**：変わった時だけ送る（`changeReport`）・値が変わらない間は 14 分半なにも来なかった＝止まりは見分けられない。登録から最初の知らせまで 22 分かかり、その間の息の変化は届かなかった。`timeOfSample` は届いた時刻の 0.2〜0.5 秒前で、1 秒に 2 件まとめて来た＝測った時刻ではなく送った時刻に見える。受けるには外から入る口（トンネル）も要る。
  - Claude のアプリの下のターミナルの窓から動かすと、Bluetooth が読めた（Claude Code の中からは断られる）。
- **11/3 の試しで分かったこと**（`docs/dev_log.md`）：
  - Bluetooth の直接の読み＝10 分で 60 回・間隔は中央 6 秒・最大 38 秒＝鮮度の線（5 分）に十分。v0.5 では主の道はクラウドの 30 秒・Bluetooth は見比べと予備（そばに機械を置ける時）。
  - クラウドの温湿度には時刻が付かず、小さな変化はすぐ上がらない＝見比べだけに使う（止まっていても見分けられない）。
  - プラグの入切＝命令の 3 秒後には状態の `power` が切り替わる＝受け手は命令の後に `power` を読み直して確かめる。
  - プラグの電流と電力は「入」の間も 0 だった＝試しでは何もつながず、プラグの LED を目で見て入切を確かめた（負荷が無いので 0 は当然）。電流で通電を確かめられるかは、加湿器（120 W）をつないだ時に見る。上がらなければ、`power` と、湿度の上がり方（30 分で +12〜16 pt）で効いたかを見る。

  4. **オートの入切**（`set_auto`＝定時の起動の `pause`／`unpause`）
  5. **止める**（`stop_all`）
  - 添える物：断った時の理由・経験の版の数と最新の要点（小さく）・今日動いた分。
- **v0.7 の並べ方**（nori が触って直した）：
  - 手動の行＝状態・入れる・切るを同じ行に。分の欄は数字の後ろに字（「[30] 分だけ」）。
  - 定時の行＝「毎日 [12:00] から [60] 分」の形に。その下に「長さを AI に任せる」の切り替えと、最後の回の分と理由（AI の分か既定の分か）。
  - オートの行＝止める（オートを切る）は改行して次の行に。
  - チャート＝**「VPD（kPa）」と「温度（℃）と湿度（%）」の 2 つの枠**に分ける（見出しつき・枠の間に余白・VPD の枠には狙いの帯を塗る・線の色を枠ごとに変える・縦の軸は枠ごとに別・時刻の軸はそろえる・穴は空白）。
  - VPD の枠の近くに 1 行＝今の外（近くのアメダスの気温・湿度）と明日の予報（天気・降水確率）。取れていなければ「天気：取れていない」。計画の理由に天気が入った時はその理由をそのまま出す。下に出典。
  - 実機デモの組で動いている時は「デモ：湿度の線は止めている」。
- **狙いの VPD は入力欄を作らない**。栽培の知識（`knowledge_seed.md` §1）から決めた帯を、チャートに帯として表示するだけ：**0.4〜0.8 kPa**（上＝0.82 kPa を越えると収量が下がるという産地の閾値の手前・下＝RH 70〜80% の目安を 15〜20℃ で VPD にした 0.34〜0.47 の間）。値は `config/saibai.toml`。
- Artifact のページは外のサイトを直接呼べない。呼べるのは MCP だけ＝**手元の受け手が自前の MCP サーバーを出し、それを Mac の Claude アプリの MCP の設定に足す**。ページは `mcp` の機能で `host:<名>` として呼ぶ（Claude アプリで開いた時だけ答える）。
- **トンネルもコネクタの登録も要らない**＝外から入る口が無い。合言葉の URL も要らない。
- **MCP の道具**：`get_status`（温湿度・VPD・読んだ時刻・プラグの状態・タイマーとオートの状態・経験の版）／`get_history`（チャート用の温度・湿度・VPD と穴）／`set_humidifier`（手動の入・切＝守りの層を通る・断った時は理由を返す）／`set_timer`（定時の入切・開始の時刻・分）／`set_auto`（オートの入・切＝11/4 までの `set_schedule` の名替え）／`stop_all`（止める）。
- ページは `get_status` を 30 秒ごとに読み直す（`refetchInterval`）。**記録はページではなく受け手が取る**＝ページが閉じていても、受け手が 30 秒ごとに読んで手元に貯める（ページは開いている間しか動かないため）。
- **MCP サーバーは薄い口**（11/4 に決めた）：Claude アプリが起動する stdio の MCP サーバーはアプリを閉じると止まる＝守りと記録は常駐の受け手が持ち、MCP サーバーは受け手に `127.0.0.1` の HTTP で聞くだけ（`src/saibai/mcp_server.py`）。受け手が止まっていれば `get_status` は `receiver.up=false` を返す。
- 先に一番細い道を通す：`get_status` だけの MCP サーバー → Claude アプリの MCP の設定 → Mac の Artifact に温湿度が出る。
- **余れば iPad**：同じ MCP サーバーをトンネル（Cloudflare Tunnel）で外に出し、claude.ai のコネクタに登録すれば、卓上の iPad からも開ける。その時は URL に長い合言葉を入れ（`.env` に置く）、守りの層の上限で最悪の時の害を限る。

## 11. デモ動画（3 分）

- **本当に動いている所だけ**で組む（ピッチの絵や説明の場面に頼らない）。
- 芯の場面：Mac の画面の Artifact に温湿度が出ている → スイッチで加湿器が入る（守りの層を通る）→ 定時（時刻も長さも人）→ **定時・長さは AI**（12:00 は人・分は経験から AI が決め、理由に経験の行を引く）→ オートを入れると、エージェントが記録を読んで計画と理由を出し、加湿器が計画どおりに入る → センサーを止まったように壊すと、守りの層が断り、エージェントが計画を直す → **農家の読み**：「明日は雨」の予報を読んで、AI が農家と同じ理由で「今日は入れない」を選ぶ → 夏と秋の再生で運転が変わる・4 通りの比較の数字。
- 字幕とナレーションは日本語。
