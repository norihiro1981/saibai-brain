## 1. 何を作るか

兵庫県の元織物工場の中で、コーヒーの幼木を育てている。毎日、温度・湿度・土の水分を見て、
「加湿器をいつ何分動かすか」「水をやるか待つか」を人が決めている。

この「毎日見て決める」仕事を、**役割の違う 3 体のエージェント**に任せる。
エージェントが出すのは**計画だけ**。計画を入／切に変えるのは、決まった規則で書いた**守りの層（コード）**。
守りの層を通った指示だけが、本物の加湿器（スマートプラグ経由）か、模擬の栽培室に届く。

### 設計の芯
- **センサーの層を、動かす機械から独立させる**。AI は機械を直接触らない。
- **どんな計画が来ても、守りの層の上限は越えない**（テストで機械的に確かめる）。
- 理由には必ず**数値と時刻**を引く。人が読む文と、機械が読む JSON の両方を残す。
- 「最適」とは言わない。季節や状態に合った運転を、データから出す（季節のモードは作り込まない）。

## 3. 全体の絵

```
  記録（CSV／実機の温湿度計）
        │
        ▼
  センサーの自己点検（コード・決定的）──────────────┐
        │ 疑わしい区間の一覧                          │
        ▼                                              │
  ┌───────────── Managed Agents ─────────────┐      │
  │  制御役（取りまとめ）                      │      │
  │   ├─ 記録の分析役（作業場の Python で集計）│      │
  │   └─ 栽培の専門家（知識を読むだけ）        │      │
  │  道具「運転の計画を出す」（custom tool）   │      │
  └──────────────────┬──────────────────────┘      │
                     │ 計画（JSON）                    │
                     ▼                                 │
           受け手（手元に常駐）◀──────────────────────┘
             │  ▲ 自前の MCP サーバー（今の状態・入切・定時の起動の入切）
             │  │
             │  └── claude.ai のコネクタ ◀── 卓上の iPad の Artifact（温湿度・スイッチ）
             │
       守りの層（決まった規則・「止める」が最優先）
             │ 入／切
          ┌──┴──────────────────┐
          ▼                      ▼
   模擬の栽培室            スマートプラグ → 加湿器
   （評価・再生）           （本物・人が付いている時）
```

- エージェントの計画（custom tool）も、iPad のスイッチ（MCP の道具）も、**同じ守りの層**を通る。

## 4. 3 体のエージェント

| 役 | モデル（仮） | 持つ道具 | 記憶 | 返す物 |
|---|---|---|---|---|
| **制御役**（取りまとめ・決める） | Opus 5.5 | 「運転の計画を出す」（custom tool）・読み取り | 栽培ノート＝書ける | その時間・その日の運転の計画・理由（数値と時刻）・状態（大丈夫／注意）・水やりの提案（人へ） |
| **記録の分析役** | Sonnet 5.5（Haiku 5.5 と比べる） | 作業場の Python・読み取り | なし | 直近の傾向・自己点検で疑わしいセンサー・前回の運転の効き目（数値と時刻つき） |
| **栽培の専門家** | Sonnet 5.5 | 読み取り | 栽培の知識＝読むだけ | 今の時期・今の状態で木が要る物・避けること・その出どころ |

- 仕事を渡せるのは 1 段まで（制御役 → 2 体）。2 体は制御役の会話を見ない＝渡す仕事に「読む場所・聞きたいこと・返す形」を必ず書く。
- 比べる相手として、**制御役 1 体が全部を自分でやる設定**も同じ指示文の骨で持つ（§7）。
- 水やりは機械で動かさない（人の作業）＝頭脳は「灌水を控える／待つ／やる」を**人への提案**として出す。

### Managed Agents の機能と、現場で要る理由（1 対 1）

| 機能 | 現場で要る理由 | 使い方 |
|---|---|---|
| 役割の違う複数のエージェント | 記録の計算・作物の知識・運転の判断は、見る物も道具も違う | 制御役＋分析役＋専門家 |
| 手元で実行する道具（custom tool） | 機械を動かす口を AI の外に置く＝守りの層を必ず通す | 「運転の計画を出す」を制御役だけに |
| 記憶の置き場（読むだけ／書ける・版が残る） | 栽培の知識は変えさせない／運転で学んだことは積み、いつ何を学んだかを後から見せる | 知識＝読むだけ・栽培ノート＝書ける |
| 作業場の中の Python | 4 週分の記録を AI の頭に全部入れない＝計算はコードで | 分析役が CSV を集計し、数値と時刻だけ返す |
| 定時の起動（cron・東京時間） | 人がいなくても毎時・毎朝決める | 毎時の見直し・毎朝 6:00 のその日の計画 |
| 1 回ごとの費用の上限 | 無人で回しても請求が暴れない | セッションに上限 |
| 出来の採点（outcome） | 計画が「理由に数値と時刻を引いているか」などを別の文脈で採点し、通るまで直させる | 毎朝の計画だけ（費用） |

使わない物：その場で役を作る機能（名簿の 3 体に固定）・大量の並列の仕組み（1 日分の記録では要らない）。

## 5. 守りの層（AI では書かない・決まった規則のコード）

| 線 | 値（再生） | 値（本物の実機・人が付く日） |
|---|---|---|
| 入れない湿度（入れる前） | `node_a` の RH が 75% 以上なら入れない | 同じ |
| 止める湿度（運転中） | 85% に届いたら計画の残りに関わらず切る | 同じ |
| 連続運転の上限 | 180 分 | **60 分** |
| 1 日の合計 | 360 分 | **120 分** |
| 入と入の間 | 30 分あける | 同じ |
| 古い値で動かさない | 最新の湿度が 5 分より古ければ入れない・運転中なら切る | 同じ（§8 の読み方で鮮度を測る） |
| 疑わしいセンサー | RH が 15 分変わらない・1 分で 10 pt 以上跳ぶ時、その値を根拠にした計画を断る | 同じ |
| 計画が来ない時 | 3 時間来なければ切 | 同じ |
| 手で止める | **すべてに優先**（iPad の「止める」・受け手の起動時は必ず切から始める） | 同じ |
| 計画に無い「入」 | — | 受け手が**毎分プラグの状態を読み**、計画に無い「入」なら切る（プラグは停電から戻ると前の状態に戻るため） |
| 人が居ない時 | — | **加湿器をプラグにつながない**（受け手と工場が両方止まると毎分の点検が効かない・加湿器は通電で運転し水切れの検知も無い）。定時の起動は、空のプラグか電気スタンドで回してよい |

- 断った時は、**断った理由を道具の結果として制御役に返す**＝制御役は直した計画を出し直せる。
- 「実運転」の再生（§7）だけは、記録をそのまま流す＝守りの層に掛けない（掛けると全部断られる）。
- **テスト**：どんな計画（ランダムに大量）を渡しても上限を越えない、を機械で確かめる。

## 6. 模擬の栽培室

- 動かすのは加湿器だけ＝**湿り気（絶対湿度）の動きだけ**を合わせる。温度は記録をそのまま流す。
- 形は単純に＝「加湿器が入っている間に足される水分」と「何もしない時に抜けていく速さ」の 2 つ程度を、加湿器の入切の記録がある日で合わせる。
- 合わせた後の誤差を README に出す（合っていない所も書く）。
- 季節で抜けていく速さが違えば、それ自体が「夏と秋で運転が変わる」理由になる。

## 7. 評価（同じ期間を 4 通りで流す）

| 通り | 中身 |
|---|---|
| 実運転 | その期間に実際にやった運転（作業の記録をそのまま）＝**お手本ではない** |
| 閾値だけ | 「湿度が◯%を下回ったら入れる」だけの単純な運転 |
| 1 体 | 制御役が 1 体で全部やる |
| チーム | 3 体 |

- **物差し**：湿り気が目標の帯に入っていた時間・加湿器の運転時間・入切の回数・守りの層に断られた回数・**センサーの故障に釣られた回数**。
- **答え合わせ**：正解は「やったこと」ではなく「後から見て正しかったこと」。正解の表は手元に置き、エージェントにも作業場にも渡さない。
- **水のやりすぎの疑い**：過去の記録を 1 日ずつ流し、**根の弱りが見えた日より前に、頭脳が土の水分の数値と時刻を引いて「控える」提案を出せたか**を数える。言い方は「疑いを早く示せた」まで。
- **先読みの禁止**：再生の各日、エージェントに渡すのは**その日までの記録だけ**。後の日の記録・根の結果・正解の表は、記憶にも知識にも入れない。再生ごとに記憶の置き場を新しく作る。
- 差が出なくても、そのまま見せる（チームにしても良くならなかった所も書く）。
- 1 回ごとに費用の上限を付ける。

## 8. 本物の口（実機）

| 物 | 役 | 読み方・動かし方 |
|---|---|---|
| スマートプラグ（SwitchBot プラグミニ） | 加湿器の電源の入／切 | SwitchBot のクラウド API（v1.1）で `turnOn`／`turnOff`・状態（電流）で本当に入ったかを確かめる |
| 温湿度計（SwitchBot 温湿度計プラス） | 木のそばの温度・湿度 | **手元の機械が Bluetooth の発信を直接読む**（数秒ごと・時刻は手元で付ける）。クラウドの値（ハブ経由）は**見比べ用**＝クラウドは 5〜30 分遅れることがあり、鮮度の線（5 分）に使えない |
| ハブミニ | 温湿度計とクラウドの橋 | クラウドの見比べ用 |

- 鍵（トークンとシークレット）は手元の機械だけ（`.env`）。リポジトリにもエージェントにも渡さない。
- **プラグは停電から戻ると前の状態に戻る**（11/3 に現物で確認：入→入・切→切）＝§5 の 2 行で受ける。
- **Bluetooth の読み取りはターミナル（か自動起動）から動かす**：macOS は Bluetooth の許可をアプリごとに分ける。Claude のアプリの中からは断られた（11/3）。受け手もアプリの外で常駐させる＝会話を閉じても守りが止まらない。
- 1 日 1 万回の呼び出しの上限＝毎分の状態の読みで約 1,440 回＝足りる。
- **11/3 の試しで分かったこと**（`docs/dev_log.md`）：
  - Bluetooth の直接の読み＝10 分で 60 回・間隔は中央 6 秒・最大 38 秒＝鮮度の線（5 分）に十分。温湿度計の主の道はこれ。
  - クラウドの温湿度には時刻が付かず、小さな変化はすぐ上がらない＝見比べだけに使う（止まっていても見分けられない）。
  - プラグの入切＝命令の 3 秒後には状態の `power` が切り替わる＝受け手は命令の後に `power` を読み直して確かめる。
  - プラグの電流と電力は「入」の間も 0 のままだった＝本当に通電したかは、まだ電流では確かめられない。加湿器（120 W）をつないだ時に見る。電流が上がらなければ、`power` と、湿度の上がり方（30 分で +12〜16 pt）で効いたかを見る。

## 9. 卓上の iPad の画面（Artifact）

- **画面＝Claude の Artifact**（iPad の Claude アプリかブラウザで開く）。今の温度・湿度（読んだ時刻つき）・加湿器の状態・**入／切のスイッチ**・**定時の起動の入／切**・今日の計画と理由・**「止める」**。
- Artifact のページは外のサイトを直接呼べない。呼べるのは claude.ai に登録したコネクタだけ＝**手元の受け手が自前の MCP サーバーを出し、それをコネクタとして登録**する。ページは `mcp` の機能で、見る人（nori）のログインのまま道具を呼ぶ。
- **MCP の道具（最小）**：`get_status`（温湿度・時刻・プラグの状態・定時の起動の状態）／`set_humidifier`（入・切＝守りの層を通る・断った時は理由を返す）／`set_schedule`（定時の起動の入・切）／`stop_all`（止める）。
- **外から届く URL**：コネクタは Anthropic のクラウドから呼ばれる＝手元の受け手をトンネル（Cloudflare Tunnel か Tailscale Funnel）で外に出す。URL に長い合言葉を入れ（`.env` に置く・リポジトリに書かない）、守りの層の上限で最悪の時の害を限る。きちんとしたログイン（OAuth）は余れば。
- **予備**：同じ道具を、手元の Wi-Fi の中で普通の Web のページからも呼べる形で作る（コネクタの道が通らない時に戻る）。
- 先に一番細い道を通す：`get_status` だけの MCP サーバー → トンネル → コネクタ登録 → iPad の Artifact に温湿度が出る。

## 11. デモ動画（3 分）

- **本当に動いている所だけ**で組む（ピッチの絵や説明の場面に頼らない）。
- 芯の場面：卓上の iPad に温湿度が出ている → スイッチで加湿器が入る（守りの層を通る）→ 定時の起動を入れると、エージェントが記録を読んで計画と理由を出し、加湿器が計画どおりに入る → センサーを止まったように壊すと、守りの層が断り、エージェントが計画を直す → 夏と秋の再生で運転が変わる・4 通りの比較の数字。
