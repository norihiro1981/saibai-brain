# 栽培室の頭脳

兵庫県の元織物工場で、コーヒーの幼木を育てています。毎日、温度と湿度と土の水分を見て「加湿器をいつ何分動かすか」「水をやるか待つか」を人が決めてきました。この「毎日見て決める」仕事を、**一度に全部ではなく、人の操作から経験を貯めながら、だんだん任せていく**頭脳です。

Built with Claude: Japan 2026 の作品です（期間 2026-11-02〜11-08 に書きました）。設計書は [`docs/design.md`](docs/design.md)、作った日々の記録は [`docs/dev_log.md`](docs/dev_log.md) です。

## 何を作ったか

- **任せ方は 4 段**です。後ろへ行くほど任せる度合いが上がります。
  1. 手動：人が画面のトグルで入れる・切る。
  2. 定時：開始の時刻も長さも人が決め、コードのタイマーが動かす（AI なし）。
  3. 定時・長さは AI：時刻は人が決め、何分動かすかを AI が決める。開始の 10 分前に聞き、答えが無ければ人の既定の分で動く。
  4. オート：時刻も分も AI が決める。3 時間ごとに起きて計画を出す。
- **頭は役割の違う 3 体のエージェント**（Claude Managed Agents）です。
  - 制御役（Opus 5.5）：計画を決めて `submit_plan` で出す。人への一言（`to_person`）も書ける。
  - 記録の分析役（Sonnet 5.5）：作業場の Python で記録を読み、操作の効き目（入れて 15・30・60 分で VPD がいくつ動いたか）を計算して、経験を書き直す。
  - 栽培の専門家（Haiku 5.5）：栽培の知識を読むだけで、出どころを付けて答える。
- オートは、起きるたびに**振り返り（経験を書く）→計画（全部読むだけ）**の 2 段のセッションを通します。経験は「いつ入れたか」の真似ではなく、「この操作でこう動いた」という効き目の事実だけです。
- **守りの層**（AI ではない、決まった規則のコード）が、どの段の計画も入／切に変えます。例：湿度 75% 以上では入れない・85% で切る・続けて 60 分まで・1 日 120 分まで・入れて 15 分たっても湿度が上がらなければ切る・「止める」がすべてに優先・起動は必ず切から。**どんな計画が来ても上限を越えない**ことを、ランダムに作った計画を大量に流すテストで確かめています。
- **農家の読み**：気象庁のアメダスと予報を受け手（コード）が取り、数行の字にして渡します。「今日だけ見ると入れたいが、明日は雨だから控える」も正しい計画として扱います。
- 画面は Mac の Claude アプリで開く Artifact（計器盤）です。手元の受け手が出す MCP サーバーを直接呼ぶので、外から入る口がありません。

```
温湿度計（クラウド 30 秒ごと）──▶ 受け手（手元に常駐）──▶ 守りの層 ──▶ スマートプラグ → 加湿器
                                    │  ▲                       ▲
                    記録の写し      ▼  │ 計画（submit_plan）     │ 手動・定時も同じ道
                         Managed Agents（振り返り→計画）          │
                                                         画面（Artifact・MCP）
```

## 動かし方

Python 3.12 と [`uv`](https://docs.astral.sh/uv/) を使います。

```bash
uv sync
```

```bash
uv run pytest
```

- 鍵（Claude の API・SwitchBot のトークンとシークレット）は `.env` に置きます（`.env.example` に鍵の名だけがあります）。プログラムの中で `python-dotenv` で読みます。
- 受け手：`uv run saibai-receiver`（既定のプラグは模擬。本物は `SAIBAI_PLUG=switchbot`）。自動起動は `sh scripts/install_receiver_agent.sh`。
- 画面の MCP サーバー：`uv run saibai-mcp`（Claude アプリの MCP の設定に足す）。画面は `artifact/status.html`。
- エージェント・置き場・環境を作る：`uv run saibai-agents setup`（評価の「1 体」は `uv run saibai-agents single`）。
- 外の天気の地点の番号は `private/weather_place.toml`（リポジトリには入れていません）。無ければ「天気は無し」で動きます。
- 評価：過去の天気を取る `uv run saibai-weather-history`・模擬を合わせる `uv run python -m saibai.sim`・再生 `uv run saibai-replay <summer|autumn> <actual|threshold|single|team>`・表 `uv run saibai-replay table`。

### 読み方（良くならなかった所も書きます）
- **夏は、どの通りでも帯の下（湿りすぎ）が 45.4 時間で同じでした**。空気がずっと湿っていて、加湿器を入れても入れなくても湿りすぎは減りません。差が出たのは乾く側の数時間だけです。帯に入っていた時間がいちばん長かったのは実運転（46.7 時間）でした。**チームにしても 1 体（43.8）より良くならず（42.3）**、どちらも閾値だけ（37.3）より長く帯に入っていました。チームと 1 体は 32 回のうち 29 回を「入れない」にし、9/5 の夕方と 9/6 の午後だけ入れました。9/6 は守りの層が 85% で 1 回切りました。
- **秋は、チーム（76.4 時間）と 1 体（76.1）がわずかに長く帯に入りました**。実運転は 69.6、閾値だけは 71.8 です。閾値だけは 1 日の上限 360 分に当たった後も 10 分ごとに出し続け、136 回のうち 113 回を断られました。チームと 1 体は断られた計画が 0 で、昼から夕方（12〜18 時台）に入れていました。
- **模擬の誤差（下の表）が、この差より大きいかもしれません**。窓の中では、模擬は加湿器の効きを記録の約 3 倍に見ています。入れて 30 分の上がりは、夏が記録 +0.38／模擬 +1.31、秋が +0.50／+1.57 g/m³ です。夏は 9/7 に加湿器の置き場を変えています。秋は 10/22 に「30 分でほとんど上がらなかった」と記録があります。加湿した通り（秋のチームと 1 体）の帯の時間は、実際より良く出ている恐れがあります。
- **センサーの故障に釣られた計画は、どの通りも 0 でした**。夏の窓には `node_a`／`node_c` の食い違いの区間が 2 つあり（9/3 15:00〜9/4 02:55）、その間に入れた運転もありません。ただし、再生では `node_c` を渡していません。釣られる機会そのものが小さかった、ということでもあります。
- 再生の天気は、その先の実際の値を予報として渡しました（**本物より有利**）。

### 人への一言（水のやりすぎの疑い）
- 制御役は `submit_plan` の `to_person` に、機械に触らない事を書けます。守りの層はこの欄を読みません。この欄で機械は動きません。再生では土の水分（`soil_a`）を記録として渡し、「何以上なら控える」の線は渡していません。
- **夏の窓では、1 体もチームも、最初の回（9/3 00:00）に、土の水分の数値と時刻を引いて「水やりを控える」と書きました。** 例（1 体）：「土の水分は 00:00 に 948 で、9/1〜9/2 の記録（910〜946）で一番湿っている。水やりは 9/2 19:00 にしたばかり。9/3〜9/4 は雨の予報。水やりは控えて、土が乾くのを待って」。
- 人の記録で「水持ちが良い」と初めて書いたのは 9/19 です。それより **16 日早く疑いを示せた**ことになります。言えるのはここまでです。効いた・当たったとは言いません。窓が 9/3 から始まるので、これより前に言えたかは測っていません。
- 秋の窓でも、両方とも最初の回（10/20 00:00）に「土 852・10/19 04:00 の水やりの後の乾き方が遅い・控えて待つ」と書きました。

## Claude Code でどう作ったか

全部を Claude Code（Opus）との会話で作りました。日ごとの細かい記録は [`docs/dev_log.md`](docs/dev_log.md) にあります。

- **設計書を先に直してからコードを書く**：作り手が段ごとの指示を出し、Claude Code はまず `docs/design.md` を直してから、段ごとに書いてテストを通し、commit と push をしました（v0.3 から v0.8 まで）。
- **本物を叩いて確かめてから本体に入れる**：SwitchBot の API（署名・状態の読み・Webhook）と Managed Agents（custom tool の往復・名簿・記憶の置き場・定時の起動・費用の上限）は、`spikes/` の試しのスクリプトで 1 手順ずつ叩きました。資料と違った所も書き残しています（例：SwitchBot の署名は README の本文でなく例のコードの形で通った・クラウドの温湿度には測った時刻が無い・エージェントを更新しても定時の起動と名簿は前の版に留まる）。Managed Agents の書き方は推測せず、Claude Code の claude-api の手引きで確かめました。
- **ランダムに流すテスト**：守りの層には、ランダムな計画・湿度の歩き・跳び・止まり・読めない区間・手の「止める」を 120 通り×2 日流し、上限を越えないことを確かめるテストがあります。再生にも「窓の中のどの時刻でも、渡した記録・経験・天気の最後の時刻が再生の時計より前」のテストがあります。テストは全部で 109 本です（`uv run pytest`）。
- **詰まった所**：
  - クラウドの湿度は整数で、工場の夜は 85 分同じ値でした。これでは「15 分変わらなければ止まり」の線が、ふつうの夜を毎晩センサーの故障とみなしてしまいました。そこで線を「温度と湿度がそろって 90 分変わらない」に変え、「入れて 15 分で上がらなければ切る」を足しました。
  - 「受け付けた」と返したのに加湿器が入らない不具合が 2 回ありました（センサーの疑いの食い違い・プラグの Wi-Fi の離線）。どちらも、理由を記録と画面に出すようにしてから直しました。
  - 模擬の栽培室は、最初は 1 本の時定数の式にしました。しかし加湿器の効き（30 分で +1.6 g/m³・切って 30 分でほぼ戻る）を 1/5 しか出せず、部屋の遅い動きと加湿器の速い霧の 2 つに分けました。
  - 地点の名や人名など、公開しない語は commit の前の門（gitleaks と語の一覧）が止めます。門に当たった時は、門を外さずに語を言い換えました。
- サブエージェントは使わず、1 本の会話で書きました。鍵（`.env`）は Claude Code の設定で読めないようにしてあります。

## データと出典

- 栽培室の記録（`data/`）は「ラズパイで集めた記録」です（夏 8/15〜9/11・秋 10/3〜10/30・約 61 秒ごと）。列と欠けは [`data/README_data.md`](data/README_data.md)。
- 外の天気：**気象庁ホームページ（アメダス・天気予報・過去の気象データ）を加工して作成**（公共データ利用規約 第 1.0 版）。地点の名と番号は書いていません（「近くのアメダス」「兵庫県の予報」と呼んでいます）。
- 再生の天気は「その先の実際の値を予報として渡した」物です。**予報がいつも当たる＝本物より有利な条件**です。
